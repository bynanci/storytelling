# 案例 A：保留兩個互斥構思，先不收斂

N-06／N-R06 · 給作者直接比較的虛構材料。尚無本案例的真人操作紀錄。

## 給作者的任務

你要規劃同一扇共用門的下一個維護窗口。這個窗口只能採取一種做法，現在不必決定。請保留下列兩個互斥構思，各自留下還沒解決的問題，不把任何構思寫成已發生或已獲同意的事。

原始觀察 S02@1：阿梅扶門，阿安收緊上方鉸鏈的一顆螺絲。S03@1：兩人只試關一次，這次沒有磨地。沒有長期測試、費用、所有權或授權資料。

| 構思 ID | 創作提議 | 未解問題 | 目前決定 |
| --- | --- | --- | --- |
| P_KEEP@1 | 先保留鉸鏈，安排一段觀察期。 | 連續使用與雨後是否仍會磨地？由誰記錄？ | 未決，不等於接受 |
| P_REPLACE@1 | 先安排更換鉸鏈，再開放下一次使用。 | 鉸鏈規格、費用與共用門授權由誰確認？ | 未決，不等於接受 |

兩案在「同一維護窗口採用的做法」上互斥；它們可以同時存在於筆記，不能因此同時被當作已選方案。新資料不足時，作者可以只補問題、延後選擇。

請回答：你會不會在下一次改稿前保留兩案？如果別人接手，怎樣看出兩案都未決？一張表是否已足夠，還是需要查詢未決問題或追蹤誰選了哪一案？

## 現有模型能表達什麼

[目前可執行的 V1 範例](brainstorm-current-v1.json) 用兩份具名口述草稿保存提案。每份都直接引用原始觀察，並把其選項標為 `creative_proposal`。未解問題與「尚未選定」目前只是文字。N-04 能在直接引用的觀察修訂後標出兩份草稿；它不會因 `based_on` 自動追蹤所有間接依賴。

```sh
./target/release/storytelling render-narrative docs/narrative/n06-cases/brainstorm-current-v1.json
./target/release/storytelling render-narrative docs/narrative/n06-cases/brainstorm-unsupported-state-v1.json
```

第二個檔案只替其中一份草稿加上 `option_state: unresolved`，示範第一個契約失敗：封閉的 V1 不接受這個欄位。即使把狀態寫進名稱，消費端也不能依契約判斷哪案仍未決、哪案已選。這是新用途的模型缺口，不是現有渲染器違反其契約。

N-04 的 `author_decision` 針對單幅插畫的創作提議，不能直接充作構思分支的選擇事件，也不能用 AI 建議自行宣稱已獲作者接受。

## 最小修改與相容性

先保留這張表與穩定的選項 ID，記錄問題、互斥集合和明確的作者選擇欄。這不需要改 Rust 或 V1。只有當作者確實要讓未決狀態跨修訂持續存在、能查詢或交接，才評估獨立的分支狀態 profile。它需引用來源／變體 ID 與 revision，並將建議和選擇分開；現有 V1 輸入和舊 N-04 歷史保持可讀。

## 驗證與成本假設

現有 CLI 探針應保留兩案、原始來源與創作標記，並拒絕未採用的狀態欄。未來若採用原生功能，驗收須包含：兩案在重播後均未被刪除；各自問題保留；一個互斥集合至多有一個明確選擇，也可保留零個選擇及未決狀態；建議不得自行接受；直接來源修訂後只將相依草稿標為待重審。

成本是假設，不是測量：熟悉本專案的一位工程師約 0.5–1 個工作日可整理文字樣板；獨立、有限的狀態／重播 profile 約 3–5 日。每工作日按六小時專注工程估算，不含招募、互動介面與正式發布。沒有實際查詢任務，信心低。
