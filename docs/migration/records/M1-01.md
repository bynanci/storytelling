## Actual source contract

- `OpenFilmProject` contains stories, timelines, media-library references and settings, but **no MediaAsset catalog**. Assuming a project JSON contains resolved assets is incorrect.
- `Composition` owns tracks, clip occurrences, duration and creative features. `Clip.id` identifies an occurrence; `assetId` identifies its reusable source. Preserve both. Clip IDs are globally unique across a composition according to `validateComposition`.
- `exportTimeline(format, composition, assets, settings?, options?)` is the actual exporter. Its JSON result is a self-contained envelope with `schemaVersion: "1.0.0"`, `composition`, filtered used `assets`, `settings`, and optional color/look metadata. This **export envelope version is independent of project schema**. It can contain future animation even while envelope remains 1.0.0; schema equality alone is insufficient.
- Application `exportWithReport` resolves catalog assets through `compositionAssets(..., true)` before calling `exportTimeline`. It checks real source status separately. None of those checks may be inferred merely by accepting the exported JSON.
- Source durations and clip source/timeline times are JS numbers in seconds. Caption cues use integer milliseconds; audio timing includes independent sample clocks. A finite importer must explicitly reject unsupported clocks/features rather than flatten them.
- `validateComposition(value, options?)` validates then returns a JSON copy. `validateProject` validates named project versions and references; `migrateProject` only defines legacy 0.1.0 defaults and otherwise validates. Do not call migration on a live project as part of read-only import.
- `resolveProjectTimebase` intentionally treats legacy decimals near NTSC rates as 1001-denominator clocks; e.g. 29.97 derives 30000/1001. Explicit timebase fields must match projected frameRate within relative 1e-9. Validation/migration preserve a legacy 29.97 declaration without persisting a derived timebase.
- Exporter `rateFraction` similarly snaps near NTSC. Preserving decimal 29.97 as exact 2997/100 in Storytelling is an **intentional delta**, not differential parity; retain original rate declaration, explicit timebase and the chosen interpretation separately.

## Recommended finite input decision

Historical research recommendation below was superseded at G2: the frozen
[finite-v1 contract](../FINITE_V1.md) admits the actual composition JSON export
with a strict allowlist. This supplies a usable existing producer, with no new
intermediate-snapshot adapter. Policy approval was obtained in the task conversation.

Prefer a deliberately named/versioned **intermediate snapshot** for M1-01 if exact decimal lexemes, reduced rational clocks and a tight allowlist are required. It must be documented as a new snapshot contract, not an existing OpenFilm project export. Carry source baseline, original composition/track/clip/asset IDs, explicit durations/trims, source declaration, and unsupported-feature inventory. Treat media URIs as opaque strings; never dereference them. Mark source hashes declared-only. No output accepted plan for rejected unsupported profile.

Alternative: directly admit the actual JSON composition export envelope, which is immediately producible by the existing consumer, but only with bounded lexeme-preserving number parsing and a complete allowlist for every nested field. Unknown creative fields (including new animation), unsupported audio, non-default transforms, locks/user overrides and metadata require explicit rejection/preservation/loss policy. Never prefilter a real source to erase unsupported features. An independently authored producer adapter that emits the intermediate snapshot is a separate piece of work if choosing the first option.
