## 2. 填寫移植比對紀錄

每項移植的 PR 應包含 `docs/migration/records/<task-id>.md`。進入實作後再建立檔案。可用下列欄位開始。

```text
任務 ID、所屬里程碑、需求 ID
來源儲存庫、完整提交識別碼、檔案路徑、Git blob 雜湊值
已閱讀的來源符號與測試名稱
目標分支的基準與提交識別碼、已有行為
責任分類：native-core / native-runtime / external-adapter / retain-host
目標狀態：absent / partial / implemented / verified
來源與授權處理、須保留的聲明
輸入及輸出格式、驗證後的型別、時鐘與時間單位
副作用與資料負責者
保留行為、刻意差異、未支援的行為
正式依賴、測試專用工具與外部執行環境
需求 ID → 新測試 → 原始測試資料與出處 → 實際結果
人工驗收與宿主實測
相依 PR、回退方式、下一項任務
```

請分開記錄上游與 Rust 端的實作狀態。M0 只檢查宣告的中繼資料。使用測試資料前，請核對使用權。公開資料中不可包含私人片段、路徑、定位資料或憑證。

## 3. 實作一項可驗收的功能

1. **G0／G1 定義範圍。** 選一個 OF 或 GAP 子任務。記下所屬里程碑、依賴、來源行為與本次排除的範圍。
2. **G2 定義契約。** 確定格式、函式簽章、錯誤碼、時間換算與失敗行為。指定資料負責者。同一個公開契約由一支 PR 統整。
3. **定位來源測試。** 執行 `rg -n '<實際符號或錯誤碼>' packages tests`。選取有效與無效案例。記下參考程式的版本。查無既有測試時，在紀錄中說明。
4. **先取得功能失敗。** 新增 Rust 回歸測試。保留首次預期失敗的結果。缺工具鏈或無法下載依賴時，記為驗證受阻。
5. **實作選定行為。** 核心演算法使用 Rust 原生實作。若轉交來源伺服器或其他外部工具執行，列出實際依賴與介面。
6. **比對兩種實作。** 執行 Rust 與 TypeScript 測試。保留原始輸出與預期結果。逐項說明差異，保留有語意的順序。
7. **驗證失敗路徑。** 依範圍選測超限、換檔、過期修訂、忙碌、取消、程序中斷或結果未知。純資料處理可在核心內驗證。
8. **準備審查。** 更新文件與需求對照。核對同一提交的 CI 結果。依授權處理 PR。發布、代簽或修改管理設定各需明確授權。

## 4. 執行驗證

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
cargo test --workspace --release --locked
cargo doc --workspace --no-deps --locked
python3 scripts/check_repo.py
git diff --check
```

儲存庫檢查會核對實作套件、直接依賴、任務來源與測試對照。M1-03 的 SHA2 依賴有獨立審查紀錄。新增介接器時，在同一支 PR 更新需求與檢查。核心與引擎應維持無 I/O 依賴。請先提供實際使用端，再建立套件。

純 Rust 切片需測試本機 CLI 能否獨立運作。測試時，從執行路徑排除 Node、Python 與 FFmpeg。TypeScript 比對與官方 OTIO Python 工具只用於驗證。宿主測試需記錄執行檔、版本、雜湊值與設定檔。每次測試使用新的隔離專案。

## 5. 可直接貼給 Codex 的指令

將 TASK_ID 換成實際任務編號。

```text
請在 bynanci/storytelling 執行 TASK_ID。
先讀 AGENTS.md、TASKS.md、ROADMAP.md 與 docs/SDLC.md。
再讀 docs/migration/OPENFILM_RUST_PORT_MAP.md、
docs/migration/NATIVE_BOUNDARIES_AND_GAPS.md 及
docs/migration/openfilm-port-index.json。

每次只交付該任務中一個尚未驗收的行為。沿用已接受的切片。
1. 同步來源與目標主線。檢查相依 PR、已接受的工作與原始重現基準。記下完整提交識別碼。
2. 讀取指定版本的原始碼、測試與既有 Rust 實作。分別記錄已有、部分實作、欠缺或受阻。
3. 完成適用的 GAP-01、02、03、16 項目。維持 MIT 授權並保留上游 Apache 授權的必要聲明。
4. 以工作表的建議路徑為起點。檢查實際檔案。在 G2 定義函式簽章、資料型別、錯誤碼、時鐘與副作用。
5. 先寫會失敗的功能測試。再用 Rust 實作此切片。純引擎不呼叫 Node、Python、SQLite 或宿主。外部介接器須明列依賴。編解碼器、GUI 與完整剪輯器留在原執行環境。
6. 留下來源與 Rust 的比對紀錄。附上測試首次失敗、實作後通過及差異比對的結果。保留既有檢查。
7. 核對同一提交的測試及 CI。缺宿主、工具、使用權或素材時，列出阻礙與解除條件。
8. 建立範圍單一的草稿 PR。若已取得合併授權且必要檢查通過，可合併並更新完成的任務。發布、標記版本及變更儲存庫政策須另有授權。

請回報任務與需求 ID、來源與目標提交識別碼、程式與測試對照、原生實作邊界、使用方式、差異類別、實際證據、待人工驗收項目及下一項任務。
```

## 6. 選擇基準與回退方式

早期規劃 PR #2 建立於 M0 PR #1 之上。當時的修改包含文件、待辦、路線圖、代理程式指引與 JSON 索引。兩支 PR 均已合併。後續任務請依主線與實際相依交付選擇基準。

用使用者能驗收的結果為 PR 命名。例如 M1-01 快照匯入、M1-02 時間軸匯出或 M1-03 宿主實測。每支 PR 只納入該結果需要的 OF 或 GAP 任務。評估原生替代方案與實際替換應分開交付。替換 FFmpeg 介接器前，先驗證品質與相容性。

依變更範圍停用新功能、恢復舊入口，或隔離本次產物。回退須保留使用者專案與主線歷史。若宿主回應未知，先讀回實際狀態，再決定是否復原。
