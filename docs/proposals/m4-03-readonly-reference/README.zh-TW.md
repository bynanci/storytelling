# M4-03 · 唯讀參考應用

[English](README.md) · [驗收情境](acceptance.md) · [Issue #109](https://github.com/bynanci/storytelling/issues/109)

**G0–G1 提案。**基準提交 `04d2ac6f5cdb43d16cc7e4c94a2ad14fad49974d`。#107 唯讀 Rust SDK 已接受。基準盤點只有 #108 的 Draft PR #151，尚無 #109 的 PR。本提案建立 M4-R03 唯讀切片的首個作者任務及可反駁的驗收條件。用戶端與資料讀取方式留待 G2 決定。

## 作者最先要完成的事

作者為粗剪交接一份缺少一個鏡頭的素材清單，另外收到一份合成剪輯提案的舊審閱。請作者指出缺少的單元及原因、找出導致舊審閱過期的改動，並告訴接手剪輯的人，目前可以安全使用哪些資料。現有答案分散於不同 CLI 或 SDK 結果；參考應用需用來源標籤及明確狀態，讓作者找到證據。

使用兩套分開標示的範例。素材覆蓋範例示範缺件。規劃與審閱使用另一套互相對應的範例，示範有效審閱及目標版本變更後的過期。既有合約沒有替兩套資料自動配對。切換到規劃頁仍可回到原本的缺件列，規劃結果不能把缺件填掉。

作者能說出缺件及原因、指出變更欄位並保留同一提案、解釋有效與過期的審閱都只能檢視，即完成本題。主持人逐題記錄完成與否、作者查看的證據、誤解、協助及未預期的原話。一次真人觀察只支持這位作者在指定場景的結果。

## 待審架構方向

| 方向 | 能驗證的範圍 | 代價或依賴 |
| --- | --- | --- |
| 本機 Rust 介面 | 直接呼叫已接受的 `consumer_v1`。第一版可用可供鍵盤和螢幕閱讀器操作的文字介面。 | 應用自行管理畫面、明確的輸入選取及有上限的讀取。先由 G2 決定實際入口。 |
| TypeScript 介面 | 可驗證網頁式操作及 transport views 的使用方式。 | 須先完成 #108 契約決策與實作驗收。 |
| 既有 SDK 範例與 CLI | 提供同一批範例的基準答案。 | 尚缺同一畫面呈現證據與切換狀態的作者任務。 |

建議把本機 Rust 介面送交 G2。屆時固定輸入選取與讀取方式、審閱失效、延遲結果、可操作入口及測試方式。唯讀切片可使用現有規劃回應、OTIO 與審閱包。新增上傳、持久化或匯出前須先說明作者需要完成的事。

## M4-R03 驗收需求草案

| ID | 可觀察條件 |
| --- | --- |
| M4-R03.1 | 透過公開 SDK 顯示敘事與修訂 ID、直接影響及素材覆蓋。缺素材保留在有效結果內，資料拒絕另顯示第一個權威診斷。 |
| M4-R03.2 | 顯示選定輸入的規劃、審閱識別，固定原始 proposal response bytes 並讀取編譯持有的審閱結果。輸入一換就撤下舊的有效標記。新輸入必須用 SDK 檢查，錯誤或舊請求晚到都不能標為目前有效。 |
| M4-R03.3 | 宣告覆蓋、審閱有效性、執行權限、Host 觀察和復原各有獨立標示。全程顯示執行不可用的原因，文字與焦點可由鍵盤和螢幕閱讀器取得。 |
| M4-R03.4 | 依明確選取有界讀取本機輸入，保留原始 bytes 與 SDK 的診斷順序。顯示識別碼及診斷時視為純文字。公開收據及預設日誌不得揭露私人位置、原始輸入或含私人值的診斷內容。 |
| M4-R03.5 | 從未來應用的一般入口重播公開範例，另外保存取得同意的匿名真人觀察。 |

以目標版本作為修訂題時，應將原本的審閱包與新 context 送給 `check_story_review`。同一份選定提案應始終保留原始 bytes，不能重新序列化。第一次產生提案時依 SDK 指引只序列化一次。歷史視圖必須標出綁定的輸入，不能讓晚到的結果更新另一組輸入的狀態。
