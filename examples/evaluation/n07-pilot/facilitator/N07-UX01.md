# N07-UX01 task draft: explicit multi-unit correction workflow

Status: proposed G0–G2 investigation, not an adopted runtime change. Requirement N-R07; source is the N-07 engineering preflight, not participant feedback.

Trigger: the N-01 identity correction changes S01 and S02 together. A ledger containing the two source_revision events rejects the second with revision.pending_review while affected variants still await review. The guard is accepted and tested; do not remove it, prefill fake variant_review events or call this a parser bug merely to finish a demo.

Question: can one bounded correction transaction preserve both old sources, identify the union of affected variants and collect the real review once the new source set is coherent? Compare this with documented sequential review and explicit before/after document snapshots. Determine author need and safety invariants before selecting an implementation.

Proposed independently testable scope, only if later adopted:

- Define source-set/transaction identity, immutable prior references, stale expected-revision rejection, pending/current boundaries and a real separate author decision.
- Positive synthetic case: two related identity corrections, no loss of old S01/S02, exact affected union and unchanged C01 scope/S03/S04.
- Negatives: fake review/AI self-confirmation, lost or stale source revision, partial transaction/replay, and an unchanged existing single-source contract.
- Measure actual metadata/repeated-input burden against the current snapshot workflow with authors. A correctness pass alone cannot establish saved author time.

No release, implementation, contract extension or N-10 mode is authorized by this draft. The next owner is maintainer/product reviewer for the G0/G2 choice; engineer estimates after invariants and actual need are frozen. Preserve the current CLI guard until that decision.
